## 7. 新会话下一步应该怎么做

1. **先读现有成果。** 在具备访问能力时，读取远端 AGENTS.md、README 和本交接文档。避免只凭旧摘要覆盖仓库新内容。
2. **一次确认最关键的产品方向。** 用简洁选择帮助用户明确上述三种平台形态，并顺便收集目标渠道、主要内容类型与自用／商业用途。不要重复讲 GitHub 的基础价值，也不要反复抛出同一个未回答的问题。
3. **收窄至 2～3 个候选。** 基于现有名单补查确实缺失的候选，检查实际所需功能、上游维护、安装条件和许可证。没有穷尽 GitHub 的必要，也不能承诺绝对检索全面。
4. **深入核验后只先跑通一个核心流程。** 例如运营工具验证“创建内容—选择平台—保存草稿／发布”的必要流程；内容网站验证发布与阅读流程。不得把 README 宣传直接当作测试结果。
5. **确认采用后保存源码与记录。** 放入适合的项目目录，保留上游许可证及版权文件，记录 URL、标签或提交 SHA、复制范围、本地改动。不要只保存一个上游链接而把用户的实际修改留在临时环境。
6. **同步交付说明。** 补齐运行命令、配置示例、验证范围、问题和下一步，更新 CHANGELOG 与根索引，再核验远端保存成功，并给用户入口。

## 8. 本次对话中可以避免的坑

### 检索与工具事实

- **公开检索与账号访问要分清。** 搜索公开项目通常无需登录；读取用户私人仓库或写入用户仓库需要相应授权。准确说明本次实际用了哪一种方式。
- **有插件不等于已授权。** 本次连接状态是通过账号信息、仓库列表和实际写入核验的，不能仅凭“安装了插件”推断成功。
- **不要把搜索结果称为全面审查。** 搜索引擎可能漏项，仓库说明也可能过时。当前五个项目只是初筛，尚无可运行性结论。
- **不要用 `size: 0` 断言仓库完全为空。** 本次后续目录读取发现已有 README；涉及内容判断时看实际文件。

### 选型与工程交付

- **先明确产品方向，再选架构。** 发布引擎、运营后台、独立媒体网站和内容社区不是同一种产品，不能只因名称接近就直接套用。
- **不要混淆开源版与收费版功能。** 特别核实 Mixpost Lite 与商业版的差异。
- **公开可见不代表任意复用。** 采用前确认具体版本许可，保留第三方声明；不在未核验时承诺可无条件闭源商用。
- **不把文档描述当成功能实测。** 国内平台接入、登录、草稿和发布是否可用，都要逐个平台核验；目前这些流程没有跑过。
- **仓库保存与运行部署是不同进度。** 代码提交成功不代表产品可运行或已上线。
- **公开仓库只放适合公开的内容。** 不上传账号密码、Cookie、API 密钥、个人数据或私有材料；`.gitignore` 不能替代实际检查。
- **保留版本与来源，而非只留名字。** 没有上游提交 SHA 和本地修改记录，后续难以复现与维护。

### 沟通、额度与跨会话衔接

- **避免重复解释、重复确认。** 用户已理解仓库价值，也已授权常规代码保存；下一会话应直接推进产品定位和选型。
- **节省额度靠控制范围。** 批量检索、复用既有结论、只精读相关文件、深查少量候选，选定后再运行；不承诺插件调用必然更省或某种套餐一定如何计费。
- **不要承诺跨会话自动记住一切。** 约定已经持久化在仓库，但新会话仍需有访问能力并主动读取 AGENTS 和相关文档。
- **状态描述要精确。** 本次已完成的是“初筛＋GitHub 连接验证＋归档规范”；原始自媒体平台建设仍待产品定位，不能报告为完成。
